# Model Orchestrator

Anthropic公式のorchestrator-workerパターンに基づき、メインセッション（Fable 5）を「采配役」に徹させ、作業をコスト最適なモデルのサブエージェントへ委譲する。

## 原則

1. **本体（Fable 5）は考える係、サブは手を動かす係。** 本体は計画・分割・委譲・統合・最終レビューに専念する。grep探索・ログ読み・大量ファイル読みなどノイズの多い作業を本体のコンテキストに入れない。
2. **サブの生ログは本体に持ち込まない。** サブエージェントには「結論のみ返せ」と指示する。中間データはサブのコンテキストで消費させ、本体には要約だけ戻す。
3. **独立したタスクは並列にspawnする。** 依存関係のないサブタスクは同一レスポンス内で同時起動する。
4. **迷ったら1段安いモデルで試し、品質不足なら上げる。** 逆（高い方から下げる）はしない。
5. **最終的な統合・整合性チェック・ユーザーへの報告は必ず本体（Fable 5）が行う。** サブの出力を無検証でそのまま採用しない。

## モデル一覧と特性（2026-06時点）

| モデル | model指定 | Input/Output ($/1M) | 特性 |
|---|---|---|---|
| Fable 5 | `fable`（本体） | $10 / $50 | 最高知能。采配・統合・超難問専用。サブには基本使わない |
| Opus 4.8 | `opus` | $5 / $25 | 高度な推論。複雑なバグ調査・設計判断・精密レビュー |
| Sonnet 5 | `sonnet` | $3 / $15 | コーディング・エージェント作業はOpus級。実装の主力 |
| Haiku 4.5 | `haiku` | $1 / $5 | 最速・最安。探索・分類・整形などの単純作業 |

コスト差は本体の1/10（Haiku）〜1/2（Opus）。サブに振るだけで大幅節約になる。

## 振り分けマトリクス

| タスク種別 | モデル | agent type | 例 |
|---|---|---|---|
| ファイル探索・コード検索・命名調査 | `haiku` | `Explore` | 「この関数どこで使われてる?」「設定ファイルを洗い出す」 |
| ログ解析・大量テキストのスキャン・分類・整形 | `haiku` | `general-purpose` | ログから該当エラー抽出、CSV整形、単純な一括置換 |
| 通常の実装・テスト作成・リファクタ・調査まとめ | `sonnet` | `general-purpose` | 機能追加、バグ修正、ドキュメント生成 |
| 複雑なバグ調査・アーキテクチャ検討・精密なコードレビュー | `opus` | `general-purpose` / `Plan` | 再現困難なバグ、設計トレードオフの比較 |
| 実装計画の立案 | `opus` | `Plan` | 大きめの変更の手順設計 |
| 計画・分割・統合・最終判断・超難問 | 本体（Fable 5） | — | サブに振らず自分でやる |

**振らない方が安い場合もある**: 1〜2回のReadやgrepで済む作業はサブを立てるオーバーヘッド（コールドスタート・コンテキスト再構築）の方が高い。本体が直接やる。目安: ツールコール5回以上 or 出力ノイズが大きい作業だけ委譲。

## サブエージェント起動の型

Agentツールで `model` パラメータを指定する:

```
Agent(
  subagent_type: "Explore",       # または general-purpose / Plan
  model: "haiku",                 # haiku / sonnet / opus
  description: "設定ファイル探索",
  prompt: <下のテンプレ>
)
```

promptテンプレ（サブは文脈ゼロで始まる点に注意）:

```
【背景】<なぜこのタスクをやるのか1-2文>
【タスク】<具体的な作業内容。曖昧さを残さない>
【対象】<パス・ファイル・範囲を明示>
【返すもの】<期待する出力形式。例: 該当ファイルのパスと行番号のリストのみ。ログや途中経過は不要>
【やらないこと】<スコープ外を明示。例: 修正はしない、調査のみ>
```

## 実行フロー

1. **分解**: タスクをサブタスクに分割し、依存関係を整理する
2. **見積り**: 各サブタスクを振り分けマトリクスでモデルに割り当てる。振り分け計画を1行ずつユーザーに提示（例: `探索→haiku×2並列, 実装→sonnet, レビュー→本体`）
3. **委譲**: 独立タスクは並列spawn。依存タスクは前段の結果を次のpromptに埋め込む
4. **検証**: サブの結果を本体が検証・統合。品質不足なら1段上のモデルで再実行
5. **報告**: 使ったモデルと委譲内容を最後に1行で報告（例: `委譲: haiku×3, sonnet×1 / 本体は統合のみ`）

## 注意

- サブエージェントは毎回コールドスタート。同じサブに追加依頼するときは新規spawnせず `SendMessage` で継続する（コンテキスト維持・再構築コスト回避）
- 書き込み系タスクを並列サブに振るときは、同一ファイルを触らないよう分割する
- セキュリティ・課金・破壊的操作を含む判断はサブに委譲しない。本体が行う
- ユーザーが明示的にモデルを指定した場合はそれに従う
